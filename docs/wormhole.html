Ploinky Wormhole

Wormhole is a protocol under development for direct communication between AssistOS workspaces. It aims to support messages, file transfers and shared tasks while each organization controls its own data and access rules.

Why connect workspaces directly?

A research team may need to send an approved result to a partner without putting both organizations' files on the same platform. Wormhole separates the service that introduces the peers from the agents that exchange their content.

This is a design for controlled communication across organizations. It is not a claim that direct connections eliminate outages, metadata exposure or security risks.

The server introduces. The local agent decides.

Ploinky Server Wormhole handles rendezvous and signaling for WebRTC connections. In the proposed design, it publishes connection information and public keys without storing message content.

Ploinky Agent Wormhole runs in each workspace. It manages identities, contacts, local policy and transfers. The receiving workspace decides whether to accept a connection and which data may leave.

Identity and contacts

A participant uses a decentralized identifier, or DID, with this format:

did:wormhole:<server-domain>:<identifier>

The public key is discoverable through the server. The private key stays with the local agent. A workspace can keep separate identities for people, Robots, projects and inboxes.

The design includes signed key-rotation records. Contacts can inspect a change and decide whether to confirm trust again. A valid signature identifies a key; the recipient still needs a policy for trusting its owner.

Mail and chat

Wormhole Mail keeps familiar fields such as subject, recipients, CC/BCC, attachments and threads. Messages are intended to be signed and encrypted end to end, with a local SQLite mailbox for storage and backup.

An unknown sender appears as a connection request. The recipient can accept, reject or block it. This gives the recipient control over admission; it does not make unwanted or malicious communication impossible.

Wormhole Chat applies the same identity and policy model to live conversations and file transfers.

Work between organizations

A supplier could send a quality report to a manufacturer. A research partner could share an approved analysis. Each workspace would apply its own rules to the request, the recipient and the exported files.

Federated learning is a longer-term use case. A coordinator would distribute a model and training plan. Each participant's DPU Agent would run the approved computation locally, keep records in LightDSU and return permitted updates through Wormhole.

Keeping raw datasets local is only part of the problem. Model updates may also reveal information, so that workflow needs export checks and separate privacy controls.

Boundaries the implementation must preserve

  • Sign and encrypt transferred content between the endpoints.
  • Keep private keys and mailbox storage under local control.
  • Make connection requests and trust changes visible.
  • Enforce each workspace's rules before it shares data.
  • Document what connection metadata the signaling service can observe.

The protocol needs implementation tests before these properties can support production claims. The Wormhole chapter describes the architecture and the federated learning chapter covers the proposed training workflow.
