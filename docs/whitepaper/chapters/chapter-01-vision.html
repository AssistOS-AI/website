Chapter 1: Vision

A useful AI worker needs somewhere to work. AssistOS aims to give people a workspace where they can delegate tasks to persistent Robots, watch progress and review the resulting files. This chapter explains the product direction. Later chapters describe the components and research behind it.

Start with a working day

Imagine a small team preparing a customer release. They have a repository, tests, a vendor website and release notes. AI can help with each task, but someone still has to move information between tools, run checks and remember what the team approved.

In AssistOS, a person could ask a Build Robot to prepare a release candidate in a separate branch. A Browser Robot could check the vendor portal. A Documentation Robot could prepare the release notes. Each task would have an owner, a working area and an output the person can inspect.

Robots, agents and packages

A Robot is the persistent worker the user sees. It has a role, a home, task history and controlled access. An AI Agent is software the Robot uses to reason and act. A Ploinky Agent is an installable capability package that may contain an AI agent, ordinary tools or a service.

This distinction lets a Robot keep its role and history when its underlying agent or model changes. Its permissions should remain separate from the capability of the new engine.

The workplace

Explorer brings files, editors, tasks and review into the same project. WebChat acts as the Copilot through which people assign and redirect work. WebMeet lets people and Robots discuss and modify a shared document, diagram or screen.

Each team should have its own controlled workspace. AssistOS workspaces and meeting rooms keep their relevant files and context together. A person can switch teams without mixing their data or giving every Robot access to every project.

Existing tools still matter. Document editors, Git, browser sessions and shared blackboards provide ways to inspect and change work that conversation alone cannot replace.

Why an IDE, and why an operating layer?

An integrated development environment puts the tools for creating and checking software together. AssistOS applies that idea to research, proposals, documents and other digital work.

An operating system manages programs, identities and resources. AssistOS aims to manage virtual workers, their homes, their capabilities and their running tasks. It runs above the host operating system and can use local machines, private servers or remote services.

Control during the work

A person should be able to observe a task, correct an instruction, pause execution or take over a browser or desktop. A Robot should stop at the boundaries set for its task. When it fails, it should report what happened and what it needs.

The result should be an artifact in the project: a patch with tests, a report with sources, a budget with calculations. Task history should explain which inputs and capabilities produced it.

Build the useful part first

Some AssistOS components work today; others remain in development or research. A reliable bounded task is the first test. Broader collaboration, capability catalogs and cross-organization communication should follow evidence from actual use.

The public vision and animated working day explain the intended experience without requiring the reader to learn the architecture first.
