Chapter 12: MRP-VM

MRP-VM means Meta-Rational Pragmatic Virtual Machine. It explores how a task expressed in natural language can become a process with explicit execution rules, checks, records and saved state.

Give the task a structure

A request such as "review this report and verify its claims" needs more than a final answer. The system should identify the inputs, select checks, record failures and know when a person must decide.

The MRP-VM design gives each program an interpreter, execution policy, trace, validator and persistent state. These provide things the user can inspect independently of the model's private reasoning.

Interpreters

Different tasks require different methods. Research interpreters may analyze literature or plan experiments. Analysis interpreters may run statistics or process genomic data. Other proposed interpreters address legal documents, security events and scientific workflows.

NeuroVSA is a research direction for representation-based reasoning. An interpreter can combine language models, exact symbolic tools and statistical checks. The language model helps interpret a request; the chosen tools perform the operations their contracts support.

Policies

A program's policy specifies allowed data, actions, outputs and required checks. It can also define audit records and human approval points.

  • Data scope limits what the interpreter may read.
  • Output rules specify format and excluded content.
  • Validation rules define acceptance conditions.
  • Approval rules identify decisions that need a person.

The runtime must enforce these limits independently of natural-language instructions. Demonstrating that enforcement is part of implementation testing.

Traces and validation

A trace connects the input files, executed steps, checks and outputs. It should record failures and interventions as well as successful work.

Structural checks test the schema and format. Constraint checks test the execution policy. Semantic checks evaluate whether the output addresses the task. Reproduction tests investigate whether a saved process can be rerun under stated conditions.

Passing one kind of check does not establish the others. A valid schema can contain a false claim, and a repeatable process can still be wrong. Failed checks should trigger correction, a stopped task or human review.

Knowledge from execution

Knowledge Units record what worked, what failed, the relevant conditions and the evidence. An interpreter could use those records to choose a method for a later task.

For example, NeuroVSA could retrieve a comparison of representations for a problem class. An evaluation agent could reuse a test that exposed a particular failure. Both need to preserve the original limits of the finding.

Relation to AGISystem2

The research explores AGISystem2 as a source of logical checks alongside MRP-VM's execution model. Formal checks apply to represented statements and constraints. They do not automatically validate every fact in a natural-language task.

The useful test is whether a person can inspect, rerun and repair a task more easily with this structure. MRP-VM remains a research and development direction rather than a universal guarantee of correct execution.
