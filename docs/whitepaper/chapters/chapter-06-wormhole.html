Chapter 6: Ploinky Wormhole

Ploinky Wormhole is a protocol under development for direct communication between workspaces. The design separates connection setup from message storage and trust decisions. Each workspace controls its identities, contacts and accepted transfers.

The problem it addresses

Two organizations may need to exchange approved files or coordinate tasks without moving all their work into the same service. Wormhole proposes a direct route between their local agents, with a server to help establish the connection.

Direct communication changes where data and trust decisions live. It does not remove network failures, hostile peers or the need to operate the endpoints securely.

Server and local agent

Ploinky Server Wormhole handles rendezvous and WebRTC signaling. The proposed server publishes connection information and public keys without storing message content or deciding which contacts a workspace trusts.

Ploinky Agent Wormhole runs inside the workspace. It manages cryptographic identities, contacts, local policies and transfers. Once the peers establish a direct channel, they exchange content through that channel. Connection metadata remains a separate privacy concern.

Mail and chat

Wormhole Mail retains subjects, recipients, CC/BCC, attachments, conversation threads, tags and filters. The design stores the mailbox locally in SQLite so its owner can back it up, migrate it or inspect it.

Wormhole Chat uses the same identity and transfer model for live conversations and files. Messages are intended to be signed and encrypted end to end.

An unknown sender appears as a connection request. The recipient can accept, reject or block it. Admission controls reduce unwanted access, but cannot guarantee that every accepted sender or message is safe.

Decentralized identifiers

A participant uses a decentralized identifier, or DID:

did:wormhole:<server-domain>:<identifier>

The server publishes the public key; the private key stays with the local agent. A workspace may use separate DIDs for people, Robots, projects and inboxes.

Signed key-rotation records let contacts inspect a change and decide whether to confirm trust again. A signature establishes control of a key. It does not establish that the holder is a trustworthy person or organization.

Coordination between organizations

A research consortium could exchange approved analyses while each partner keeps its source data locally. A supply chain could use the same mechanism for purchase orders, shipping updates and quality reports. Each workspace would enforce its own rules before a transfer.

Federated learning is a further research direction. A coordinator would distribute the model and plan. Each participant's DPU Agent would run the allowed training task locally, store its records in LightDSU and return approved updates through Wormhole.

Model updates can also leak information. That workflow needs privacy and export checks in addition to encrypted transport.

Boundaries to test

  • The signaling service should not receive plaintext message content.
  • Local agents should retain private keys, mailbox storage and contact policy.
  • Peers should verify signatures and apply access rules before accepting transfers.
  • Workspaces should record key changes, approvals and relevant transfer events.
  • The deployment should document its connection metadata and network dependencies.

These are design requirements, not audited guarantees. The public Wormhole overview introduces the idea; the federated learning chapter describes the proposed training protocol.
