Chapter 15: Agentic Knowledge Units (AKU)

AKU — Agentic Knowledge Units — is the context management system that organizes agent memory and knowledge in an explorable, user-controllable way. Instead of relying on opaque vector embeddings or external RAG services, AKU uses deterministic local indexing and BM25F keyword search to make agent memory transparent, auditable, and fast.

The Problem with Agent Memory

Today's AI agents have a fundamental memory problem: they either forget everything between sessions, or they rely on external vector databases that are opaque, expensive, and hard to audit. When an agent produces a finding, writes a specification, or runs an experiment, that knowledge should persist — not as a black-box embedding, but as a structured, searchable, reusable unit.

AKU solves this by introducing Knowledge Units (KUs) — discrete units of agent knowledge that live in a hidden .aku/ folder within any project, workspace, or experiment directory. Each KU has its own folder with metadata, state, history, documents, results, and supporting files. But search never opens individual KU folders — it reads aggregated index files at the root level, making it fast even with thousands of KUs.

How AKU Works

The structure is simple:

<root-folder>/.aku/ contains:

  • search-index.jsonl — the main denormalized search index, containing all searchable metadata from every KU, document, result, and event.
  • search-stats.json — BM25F statistics: document counts, field lengths, term frequencies.
  • ku-index.jsonl, documents-index.jsonl, results-index.jsonl, events-index.jsonl — specialized indexes for different record types.
  • kus/ — individual KU folders, each with manifest.json, state.md, history.md, and subfolders for documents, results, code, and data.

When an agent needs context, it calls buildContextPack(query, options). AKU reads the root-level index, applies BM25F scoring with exact keyword boosts, filters by type and status, controls diversity, and returns a compact context pack within a character budget. The agent gets relevant knowledge without being overwhelmed.

BM25F Search

AKU uses a simplified BM25F — BM25 with weighted fields. Different fields carry different importance:

  • keywords (weight 8) — explicit terms defined by the agent.
  • tags (weight 6) — categorical labels.
  • title (weight 5) — the KU or document name.
  • reusable_findings (weight 4) — short conclusions useful for future agents.
  • summary (weight 3) — brief description.

Exact phrase matches receive significant boosts: +60 for exact keyword phrases, +45 for exact tag matches, +40 for exact title phrases. This ensures that when an agent searches for "BM25F context pack," records with those exact keywords rise to the top — not just records that happen to mention the words in passing.

Knowledge Unit Types

AKU supports many KU types, each representing a different kind of agent knowledge:

  • experiment — simulations, benchmarks, tests, empirical validations.
  • specification — technical, functional, architectural, or API specs.
  • scientific_article — articles, position papers, whitepapers.
  • architecture_decision — technical decisions with justifications.
  • research_note — ideas, hypotheses, conceptual notes.
  • data_analysis — data verification and interpretation.
  • validation — conceptual, technical, or documentary validations.
  • reusable_pattern — technical or methodological patterns worth reusing.
  • failure_note — informative failures worth preserving.

ContextPack: Compact Agent Context

The ContextPack is the object through which AKU delivers relevant information to an agent without overwhelming its context window. It respects a character budget, prioritizes KUs over history, summarizes documents and results, and includes a matched_on explanation for each result so the agent understands why something was selected.

Levels of detail are available:

  • L1 — results directly from search-index.jsonl (default).
  • L2 — state.md for selected KUs (activated with includeState: true).
  • L3 — full documents or results (explicit request).
  • L4 — history.md (explicit reconstruction of evolution).

Why Deterministic, Not Vector-Based

AKU deliberately avoids embeddings and vector search for several reasons:

  • Transparency: BM25F scoring is explainable. An agent can see exactly why a result ranked high — which fields matched, which boosts applied.
  • Speed: Reading a JSONL index and computing BM25F is fast, even with thousands of records. No external service, no GPU, no latency.
  • Control: Agents and skills decide what KUs to create, what conclusions to preserve, what to delete. AKU provides the infrastructure, not the semantics.
  • Portability: The entire memory is a folder structure with JSON files. It can be versioned, backed up, shared, and inspected with any text editor.

Vision

AKU represents a different approach to agent memory: not a black-box embedding service, but a transparent, deterministic, local library. Every KU is a structured unit of knowledge with metadata, state, history, and findings. Search is fast because it reads aggregated indexes, not thousands of folders. Context is compact because it respects character budgets and diversity controls. And everything is auditable because it lives in plain files that any developer can inspect. This is agent memory you can trust, understand, and control.
