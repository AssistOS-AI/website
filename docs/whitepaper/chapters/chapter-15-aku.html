Chapter 15: Agentic knowledge units

Agentic knowledge units, or AKU, organize reusable agent context in local files. Aggregated indexes and BM25F keyword search select records for a task without requiring an external search service.

Keep a finding with its evidence

An experiment, specification or failed attempt can help a later task. A Knowledge Unit gives that material a folder with metadata, state, history, documents, results and supporting files.

The proposed library keeps these units in .aku/ beneath a project, workspace or experiment directory. Search reads aggregated indexes before opening the selected unit's detailed files.

Directory structure

  • search-index.jsonl contains searchable metadata from units, documents, results and events.
  • search-stats.json contains document counts, field lengths and term statistics.
  • ku-index.jsonl, documents-index.jsonl, results-index.jsonl and events-index.jsonl organize the record types.
  • kus/ contains individual folders with manifest.json, state.md, history.md and supporting documents, results, code and data.

Build a context pack

An agent calls buildContextPack(query, options). The library scores the root-level index, filters by type and status, applies diversity controls and selects a result within a character budget.

The ContextPack prioritizes Knowledge Units over history and includes a matched_on explanation. A reader can inspect which fields matched instead of treating the ranking as unexplained output.

Search weights

The documented BM25F configuration assigns these field weights:

  • keywords: 8
  • tags: 6
  • title: 5
  • reusable_findings: 4
  • summary: 3

Exact keyword phrases add 60 points, exact tags add 45, and exact title phrases add 40. These boosts favor explicit matches. They do not establish the truth or usefulness of the matched record.

Record types

The type vocabulary includes experiment, specification, scientific_article, architecture_decision, research_note, data_analysis, validation, reusable_pattern and failure_note.

Agents and skills decide what to save, validate or remove. The library supplies storage and retrieval; it does not decide which conclusions deserve trust.

Levels of detail

  • L1 returns records from search-index.jsonl by default.
  • L2 adds selected state.md files with includeState: true.
  • L3 opens full documents or results on request.
  • L4 opens history.md to reconstruct how a unit changed.

Why local keyword search?

Files and explicit scores let developers inspect the ranking and version or back up the knowledge store. Search does not require a GPU or remote request. Its runtime cost still depends on the index and query.

This is a choice for inspectable project context, not a claim that keyword search is best for every retrieval problem. The library and its task-specific evaluation remain part of the development work.
