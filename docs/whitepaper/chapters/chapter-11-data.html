Chapter 11: Data sharing and provenance

LightDSU and the DPU Agent describe how AssistOS can store sensitive data locally, control computations on it and preserve a record of its use. Data-space adapters and a sharing plugin extend that design across organizations. These integrations remain in development.

LightDSU data units

LightDSU stores data in encrypted, content-addressed blocks called bricks. A BrickMap records the virtual file structure, references to those blocks and the symmetric keys needed to reconstruct them. A signed, append-only event log anchors the unit's history.

The key hierarchy derives three access types from a master secret:

  • lkey grants full control, including writing, granting, revoking, reading and verification.
  • rkey provides read access to the BrickMap and files, plus anchor verification.
  • lza permits verification of the anchor's existence and history without content access.

This separates proof of history from permission to read or modify the data. It does not make previously disclosed content retractable.

Provenance profiles

Detailed provenance records use encrypted bricks referenced by compact anchor events. The proposed profiles cover different kinds of records:

  • LIGHTDSU_MINIMAL records the operation, resource, actor, time, inputs and outputs.
  • W3C_PROV represents entities, activities and agents.
  • FHIR_PROVENANCE and FHIR_AUDIT_EVENT cover healthcare provenance and audit records.
  • GXP_AUDIT_TRAIL organizes evidence for pharmaceutical and regulated workflows.
  • GA4GH_DATA_USE describes genomic data-use terms.
  • RO_CRATE describes research objects and their metadata.
  • AI_ML_EXPERIMENT connects datasets, models, code, parameters, metrics and results.

A profile provides a record format. Whether it meets a sector's requirements needs domain-specific validation.

DPU Agent

The DPU Agent keeps sensitive data in its local environment and exposes controlled operations. Requesting agents use references such as packageRef, taskRef and resultRef rather than receiving raw data by default.

  • The Secret Vault holds encrypted credentials and supplies them to authorized tasks.
  • The Confidential Object Store applies Access, Read, Comment and Write permissions to files and folders.
  • The LightDSU Package Store manages encrypted packages, grants and policies.
  • Sandboxed tasks process the permitted data and return approved outputs.
  • Audit records connect access, tasks, exports and policy changes.

European Data Spaces

The EDS Adapter Agent is intended to search DCAT/DCAT-AP catalogs, describe datasets and usage policies, request access and prepare transfers. It converts external records into dataset descriptions, policy summaries, grants and transfer plans.

The DPU Agent would receive approved imports, create encrypted LightDSU packages, apply local policy and record subsequent work. The adapter handles external connections; the DPU handles local data access.

The sharing plugin

The proposed Data Sharing Plugin has screens for shared-data records, FAIR metadata creation, network search, and requests and bookmarks. A local Data Sharing Agent performs its operations through MCP tools.

The metadata form records title, description, domain, keywords, data type, provenance and access restrictions. Metadata can be published in a dedicated GitHub repository without publishing the dataset itself.

Other researchers can discover that record and request access. An approved transfer could use Wormhole. This separation makes discovery possible while leaving the data owner responsible for the sharing decision.
