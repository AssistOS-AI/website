Chapter 11: Data Sharing & Provenance

LightDSU is the encrypted data substrate of the Ploinky ecosystem — a local library for storing, versioning, auditing, and controlling access to encrypted data units. Together with DPU Agent, European Data Spaces integration, and the Data Sharing Plugin, it forms a complete architecture for sensitive data management, provenance tracking, and controlled sharing across organizations.

Encrypted Data Units: LightDSU

LightDSU stores data as encrypted bricks — content-addressed blocks that can only be reconstructed with the right keys. A special brick called the BrickMap maintains the virtual file system structure, references to data bricks, and the symmetric keys needed for reconstruction. The entire system is anchored by a cryptographically signed, append-only event log.

Access is controlled through three types of keys, derived hierarchically from a single master secret:

  • lkey — full control: write, grant, revoke, read, verify.
  • rkey — read-only: decrypt the BrickMap, read files, verify the anchor.
  • lza — zero-access: verify the anchor's existence and history without seeing any content.

This hierarchy enables a powerful pattern: you can give someone proof that a dataset exists and has a certain history (lza) without giving them access to the data itself. You can grant read access (rkey) without giving write privileges. And you retain full control (lkey) for administration.

Provenance Profiles

Every operation on a LightDSU data unit produces a signed event in the anchor. For detailed provenance, LightDSU supports multiple profiles — each mapping to established standards for different domains:

  • LIGHTDSU_MINIMAL — lightweight provenance for technical audit: what operation, on what resource, by whom, when, with what inputs and outputs.
  • W3C_PROV — general provenance interoperability using the W3C PROV model of entities, activities, and agents.
  • FHIR_PROVENANCE / FHIR_AUDIT_EVENT — healthcare and clinical data provenance using HL7 FHIR standards.
  • GXP_AUDIT_TRAIL — pharmaceutical and regulated environments, supporting FDA 21 CFR Part 11 and EU GMP Annex 11 requirements.
  • GA4GH_DATA_USE — genomic data with standardized usage terms through the GA4GH Data Use Ontology.
  • RO_CRATE — FAIR research objects and publishing using RO-Crate metadata.
  • AI_ML_EXPERIMENT — machine learning experiment provenance: datasets, models, code, parameters, metrics, and results.

Each profile is stored as an encrypted brick, referenced by the compact anchor event. The anchor stays small and inspectable; the detailed provenance stays encrypted and domain-specific.

DPU Agent: Protecting Sensitive Data

DPU Agent is the data protection component of a Ploinky workspace. It owns sensitive data locally and exposes it to other agents only through controlled interfaces. Research agents never receive raw data — they receive references: packageRef, taskRef, resultRef.

DPU Agent manages:

  • Secret Vault — API keys, passwords, tokens, credentials. Secrets are encrypted at rest and injected into tasks, not exposed to agents.
  • Confidential Object Store — files and folders with granular permissions (Access, Read, Comment, Write) modeled after Google Docs-style sharing.
  • LightDSU Package Store — encrypted data packages with policies, grants, and provenance.
  • Sandbox Execution — tasks run over sensitive data in isolated environments. The requesting agent gets only the permitted output, not the raw data.
  • Audit & Provenance — every access, task, export, and policy change is logged and verifiable.

European Data Spaces Integration

Ploinky integrates with European Data Spaces through two cooperating agents:

EDS Adapter Agent is the external-facing component. It searches DCAT/DCAT-AP catalogues, describes datasets, summarizes usage policies, initiates access requests, attaches grants, and prepares imports. It translates external data-space concepts into stable Ploinky primitives — dataset descriptors, policy summaries, access grants, and transfer plans.

DPU Agent receives approved data and materializes it as encrypted LightDSU packages. It enforces policies, runs sandboxed computations, and records provenance for imports, transformations, and results.

The separation is deliberate: the adapter handles external interoperability; the DPU handles sensitive data locally. Research agents operate through DPU task tools and never require direct access to external data spaces or raw sensitive data.

Data Sharing Plugin

The Data Sharing Plugin provides a minimal UI for researchers to publish FAIR metadata descriptions of datasets, search metadata published by others, and request access to relevant data. All operations are executed by a local Data Sharing Agent through MCP tools.

The plugin has four screens:

  • My Shared Data — datasets the user wants to make visible through metadata.
  • Create FAIR Metadata — guided form for generating metadata: title, description, domain, keywords, data type, provenance, access conditions, ethical/legal restrictions.
  • Search Data Network — search in the local index built from metadata published by the user and discovered through other agents in the Ploinky network.
  • Requests & Bookmarks — saved datasets, sent requests, received requests, and their status.

Metadata is published to a dedicated GitHub repository — without publishing the raw data. Other researchers can discover the metadata, request access, and if approved, receive the data through Ploinky Wormhole's secure P2P channels.

Vision

Together, LightDSU, DPU Agent, EDS Adapter, and the Data Sharing Plugin form a complete data sovereignty stack: encrypted storage with verifiable provenance, controlled access through sandboxed execution, interoperability with European Data Spaces, and a discovery layer that connects researchers through metadata — not through exposed data. The result is a system where data can be shared, analyzed, and trusted without ever leaving the control of its owner.
